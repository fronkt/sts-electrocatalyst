## Why there are no expected census values here

Writing them would mean writing a per-atom / per-axis / per-step force-block
parser — which is `silentgate/readers/*`, which is core (docs/43:1840) — and
would put a second, unreviewed detector in the repo, leaving a real question
(*whose census is right?*) with no registered answer. A9.2 exists to catch
exactly that failure mode.

So the manifest records **structural** facts only: hashes, byte counts, marker
lines, block counts. Numeric expectations enter later as **golden files**
generated by the entrant's core and reviewed by him.

Hashes are LF-normalised. `.gitattributes` gained `*.out text eol=lf` on
2026-09-04, so *new* checkouts are LF everywhere — but files checked out before
that rule existed still carry CRLF in the Windows working tree until they are
renormalised (e.g. `runs/Co_slab/H2.out`: 464 CR bytes in the worktree, 0 in the
blob). With `core.autocrlf=true` on the entrant's machine the same tracked blob
can therefore still be CRLF locally and LF on Linux CI, so every content check
normalises first and will keep doing so.

## The seven skips

`test_open_questions.py` skips while `silentgate/` is absent — a question about
how to score the core cannot bind before the core is written. The moment the core
is committed they become failures until each ruling is recorded with its dated
line. Today's red is carried by the control face, not by this suite: the suite
checks that the *harness* is sound, so if it ever goes red that is a real
regression.
